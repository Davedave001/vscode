# Windows native development build

Run the fork from the checkout with its own profiles:

```powershell
node scripts/code-agent-workspace.ts
```

Use `--ide` to start in the editor, `--workspace "D:\Your Project"` to choose an existing folder, or `--dry-run` to inspect the executable and arguments without creating profiles or opening a window. The launcher requires a prepared `.build/electron/Code - OSS.exe` and compiled client/extensions. Node 24 can run its TypeScript directly.

The launcher places editor settings, installed extensions, shared storage, Codex configuration, and Claude configuration under separate `agent-workspace-*` directories in `.build`. It clears inherited `VSCODE_*` variables and `ELECTRON_RUN_AS_NODE` so the fork does not reuse another editor's IPC or runtime overrides. A new isolated profile enables native Codex; connect a ChatGPT account through Agent Subscriptions. The optional Claude Agent SDK provider starts disabled; Claude subscriptions use the official Claude Code client through that same menu. Existing settings are never replaced. Credentials are not copied into these directories.

After launching the updated main process, its Windows protocol command retains explicitly selected editor, extension, and shared-storage paths. The launcher also supplies `--agent-codex-home` and `--agent-claude-config-dir`; startup resolves those explicit paths against its original working directory and restores `CODEX_HOME` and `CLAUDE_CONFIG_DIR` for this instance. The normalized arguments are retained in Windows protocol registration, so a cold URL launch uses the same SDK homes without inheriting the launcher's environment. Without these arguments, existing ambient homes and configuration behavior remain unchanged. The registration uses Electron's argument quoting instead of embedding quote characters in the app path. Other launcher environment variables are not serialized. The pinned [Electron Windows implementation](https://github.com/electron/electron/blob/v43.8.9/shell/browser/browser_win.cc) builds the command using its [argument quoting helper](https://github.com/electron/electron/blob/v43.8.9/shell/common/command_line_util_win.cc).

Run `node scripts/test-agent-workspace-protocol-registration.mts` after building the client for a bounded Windows registration check. It starts a hidden, minimal Electron controller with fixture storage, verifies that a unique test-only protocol key is absent, registers that scheme, and executes its stored command through `CreateProcessW` without a shell. A probe records the received argument array and exits before creating a window. The check covers spaces, shell metacharacters, trailing path separators, all three storage flags, and a URL with query and fragment delimiters. It removes the complete test key, verifies the real `signal-c` command stayed unchanged, closes its controller, and retains a report under `.build/agent-workspace-protocol-registration/`. It does not open the real fork or verify account sign-in.

## Native library preparation on this machine

The native modules target Electron 43.8.9, Node 24.22.1, ABI 148. Repository preinstall prepared the runtime headers. The installed VS 2026 compiler is MSVC 14.51.36231, but its Spectre libraries were absent. Microsoft's existing Visual Studio catalog identifies the matching package:

- Package: `Microsoft.VC.14.51.CRT.x64.Desktop.spectre.base`, package version `14.51.36252`.
- Archive SHA-256: `1d047253e126107611557d8604764aa57d58e81d9e36593f1f2b2d687aeaace9`.
- Source: the HTTPS payload URL in `C:\ProgramData\Microsoft\VisualStudio\Packages\_Instances\de48834c\catalog.json` on `download.visualstudio.microsoft.com`.
- Verified archive and provenance: `.build/native-spectre/`.
- Extracted libraries: `.build/native-spectre/extracted/Contents/VC/Tools/MSVC/14.51.36231/lib/spectre/x64/`.

The archive hash was checked against the catalog before extraction. Native builds passed the extracted directory as both MSBuild global properties `VC_LibraryPath_VC_x64_Desktop_spectre` and `VC_LibraryPath_VC_Desktop_CurrentPlatform_spectre`. The policy-watcher compiler log includes `/Qspectre`, and its linker input log confirms `libcmt.lib`, `libcpmt.lib`, and `libvcruntime.lib` came from the extracted Spectre directory. No mitigation was disabled and the installed compiler files were not modified.

MSBuild must receive a solution's physical pnpm package path rather than the root `node_modules` symlink: generated relative project references are resolved from that physical directory. Modules without a solution were configured with the repository's pinned Node, the existing node-gyp, `--target=43.8.9 --arch=x64 --dist-url=https://electronjs.org/headers`, and the prepared header cache. Supplying `--nodedir` directly made node-gyp choose `Release/node.lib`; normal target configuration correctly selected the cached `x64/node.lib`.

## Validation and limits

- Fifteen native dependencies loaded successfully in the fork's actual Electron runtime, including policy-watcher, SQLite, spdlog, windows-mutex, windows-process-tree, native-watchdog, node-pty, deviceid, windows-registry, fs-copyfile, native-is-elevated, native-keymap, windows-foreground-love, kerberos, and Parcel watcher.
- A full `build-fast` build completed, including client resources, built-in extensions, and the Copilot extension. This resolved the missing npm extension output identified during the first native launch.
- The native Agents window was observed rendering the labelled Agents/IDE switch, Attention Queue, Session Tools, workspace picker, local agent controls, and file/tool tabs. This proves a running development window, not a packaged release or a completed model-backed task.
- Launcher tests cover inherited-environment isolation, separate storage arguments in both modes, and a dry-run with a workspace path containing spaces. Targeted strict type checking and lint passed.
- The initial direct launch used the default Code OSS shared-storage path and allowed SDK discovery from the ambient agent configuration. The dedicated launcher corrects those defaults for subsequent launches. Existing global data was preserved.

Manual test: launch with the command above, press Ctrl+K then Ctrl+Shift+A from Agents, and confirm the IDE opens the selected workspace. Use the matching switch or shortcut to return to Agents.

For an isolated native continuity check after building the client, run `node scripts/test-agent-workspace-native.mts` on Windows. It uses the prepared executable, a new fixture profile and separate agent homes, in-memory secret storage, and hidden windows. It verifies two Agents/IDE round trips retain the original multi-root editor, its dirty untitled buffer, and the Agents draft. It neither reuses an installed editor profile nor signs into a provider. The script retains screenshots and a report under `.build/agent-workspace-native-smoke/` and closes only its own launched application. Hidden captures use Electron's `capturePage` with `stayHidden` enabled, as documented in the [Electron webContents API](https://www.electronjs.org/docs/latest/api/web-contents#contentscapturepagerect-opts).

Use `node scripts/test-agent-workspace-native.mts --empty-workspace` for the folderless variant. It starts from the empty Agents composer, opens one editor, adds a dirty buffer, and verifies repeated mode switches reuse that window without losing either draft.

Use `node scripts/test-agent-workspace-native.mts --conversation` to complete a native SDK conversation against the loopback mock endpoint, restore its visible response in the IDE, then retain that conversation, a follow-up draft, and an unsaved editor buffer through two round trips. The report records conversation completion and restoration plus model-request counts before and after handoff; restoration must not send another request. This uses a registered mock response and an explicitly selected mock model with synthetic credentials, without copying account profiles. It does not verify real provider sign-in or Auto routing. Test the mock model-catalog contract separately with `node --test scripts/chat-simulation/common/mock-llm-server.test.mts`.

Use `node scripts/test-agent-workspace-native.mts --protocol` to extend that conversation scenario with external editor-link delivery. It closes the first editor, delivers the folderless conversation link through a secondary CLI into the running fixture, checks two mode round trips, then restarts only the fixture application with the same link and profile to check persisted cold restoration. Cold startup must recover the dirty buffer and restore the conversation in exactly one editor, without sending another model request. All windows remain hidden. Every native-smoke variant uses its own portable directory, which also confines `argv.json` and disables OS protocol registration; the running process confirms its portable and editor-storage paths. The fixture alone disables local/remote protocol confirmation dialogs; separate unit tests cover the default prompt, denial, and preference persistence. This direct `--open-url` delivery verifies the native receiver without requiring a browser or an OS protocol association. It does not prove installed browser-to-app association, remote-host connectivity, or real provider sign-in.

Use `node scripts/test-agent-workspace-native.mts --workspace-protocol` for a conversation link carrying both fixture workspace roots. It additionally checks both roots in the Explorer, sends a second link with reversed root order to verify matching-editor reuse, and verifies the conversation and dirty buffer after cold workspace recovery. The cold launch removes `CODEX_HOME` and `CLAUDE_CONFIG_DIR` from its inherited environment and asserts both were restored from explicit arguments. The fixture supplies its own process home and AppData directories as well as explicit SDK storage, because workspace-less chat scratch directories derive from `os.homedir()`. A child-process check confirms that home resolution stays in the fixture. Failure diagnostics use hidden native captures and bounded DOM text from these synthetic test windows.
